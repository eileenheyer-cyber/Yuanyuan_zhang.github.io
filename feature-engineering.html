Feature Engineering: Turning Raw Data into Meaningful Features

A practical guide to feature creation, transformation, selection, and preprocessing in machine learning.

Imagine an online shop that wants to know which customers will stop buying. Its database holds one row per order: a customer ID, a timestamp and an order value. You can't feed that table to a model. It has the wrong shape (one row per order, not per customer), and the columns say little about behavior. A timestamp such as 2026-06-12 14:03 is just a number that keeps growing.

Now compare it with "this customer last ordered 7 days ago, orders about once a month and spends €45 per order". Same data, but now it contains information a model can use.

Why Feature Engineering Matters

Feature engineering is the work of turning raw data into inputs (features) that make a pattern easier for a model to learn. It sits between data quality and model choice. Clean data is the precondition, and the representation you choose decides how much of the signal the model can actually see. A simple model with good features often beats a complex model fed with raw columns.

This article follows one scenario: predicting customer churn for an e-commerce shop. First we clarify what a feature is, then go through the core techniques, build customer features in Python, select among them, wrap everything in a leakage-safe pipeline, and test whether the effort paid off.

Understanding Features

A feature is an input column the model uses to make a prediction. The target variable is what you want to predict, here churned (1 = no order in the next 90 days, 0 = ordered again). Features can be numerical (order value, age) or categorical (country, product category). Raw features are the columns as recorded. Engineered features are derived from them.

Raw featureEngineered featureWhat the model gains
order_timestampdays_since_last_orderRecency instead of a growing number

Core Feature Engineering Techniques

Three terms keep the next sections tidy. Feature creation builds new columns (ratios, aggregates). Feature transformation changes the form of an existing column (log, scaling, encoding). Feature selection removes columns (see Feature Selection and Feature Importance below).

A. Numerical transformations

Log transformation. Order values are skewed: most orders are €20–60, a few are €900. Taking the logarithm pulls the long tail in, so one huge order stops dominating a linear model. Use log1p (the log of 1 + x), which also works for zeros. It suits right-skewed, non-negative values, mainly with linear models. Tree-based models don't need it, and a logged value is harder to explain to stakeholders.

df["log_order_value"] = np.log1p(df["order_value"])

Standardization and normalization. Standardization rescales a column to mean 0 and standard deviation 1. Min-max normalization squeezes values into the range 0 to 1.

z = x − meanstandard deviation

The z-value says how many standard deviations a customer sits above or below the average, which puts "total spent" in euros and "orders per month" on the same footing.

x′ = x − minmax − min

The min-max value says where a customer sits between the lowest and highest value. Both matter when the model is sensitive to scale (logistic regression, k-nearest neighbors, PCA, regularized models), because otherwise a column measured in large numbers outweighs a small one simply by size. Trees ignore scale. Min-max is sensitive to outliers, because one extreme value squeezes everyone else together.

from sklearn.preprocessing import StandardScaler, MinMaxScaler

z = StandardScaler().fit_transform(df[["order_value"]])    # mean 0, std 1
mm = MinMaxScaler().fit_transform(df[["order_value"]])     # range 0 to 1

Binning. Binning cuts a numerical column into groups, such as low, mid, high and top order value (quartiles). It helps when the effect isn't smooth (for example, age groups with different behavior) and when you want something easy to explain. The cost is lost detail: two customers just either side of a cut-off look completely different, and two very different customers in one bin look identical.

df["value_band"] = pd.qcut(df["order_value"], q=4, labels=["low", "mid", "high", "top"])

B. Categorical encoding

Models need numbers, but the way you turn categories into numbers can add information that isn't there. One-Hot Encoding explains this in detail with a product-category example. In short:

EncodingIdeaUse whenLimitation
One-hotOne 0/1 column per categoryFew categories, no order (country, category)Many categories mean many columns
LabelOne integer per categoryOnly for the target (0/1)On features it invents an order
OrdinalIntegers in a meaningful orderA real order exists (S < M < L)You must specify the order yourself
TargetCategory replaced by its average target valueMany categories (e.g., postcode)Leaks the target if done naively
 
from sklearn.preprocessing import OrdinalEncoder, TargetEncoder

pd.get_dummies(df["category"], prefix="cat")                                # one-hot
OrdinalEncoder(categories=[["S", "M", "L"]]).fit_transform(df[["size"]])    # ordinal

te = TargetEncoder(target_type="binary", cv=5)                              # target
df["category_te"] = te.fit_transform(df[["category"]], df["churned"]).ravel()

Target encoding is the one to handle with care. If a category's average churn rate is computed on the same rows the model then trains on, the feature contains the answer. scikit-learn's TargetEncoder reduces this with internal cross-fitting inside fit_transform, but it must still be fitted on training data only.

C. Date and time features

Dates carry several kinds of information once you pull them apart.

  • Calendar parts. Year, month, weekday, hour, and a weekend flag.
  • Time since an event. Days since the last purchase is the most useful date feature in churn problems.
  • Cyclical encoding. Weekday, month and hour are circular. Hour 23 is next to hour 0, but as plain numbers they are 23 apart. Encoding the hour as a sine and a cosine of its position on the 24-hour circle fixes that.
df["weekday"] = df["order_ts"].dt.weekday
df["is_weekend"] = (df["weekday"] >= 5).astype(int)
df["hour"] = df["order_ts"].dt.hour
df["hour_sin"] = np.sin(2 * np.pi * df["hour"] / 24)
df["hour_cos"] = np.cos(2 * np.pi * df["hour"] / 24)

Use cyclical encoding with linear and distance-based models. Trees can usually cope with plain integers. The sine/cosine pair is harder to read than "hour = 23", so use it only where the circular distance matters.

D. Feature creation

New columns built from existing ones often carry the most domain knowledge.

  • Ratios. Order value per item, or recency divided by a customer's usual gap between orders. A customer who has been silent for 60 days but normally orders every 55 days is fine. One who normally orders every 10 days is not.
  • Interactions. The product of two features, such as order value × weekend flag, when the effect of one depends on the other.
  • Aggregations. Summaries over groups, such as a customer's total spending or a category's average order value.
  • Domain-specific features. Anything the business already knows matters, such as "used a discount code" or "returned an item".
df["value_per_item"] = df["order_value"] / df["items"]
df["category_mean_value"] = df.groupby("category")["order_value"].transform("mean")
df["value_vs_category"] = df["order_value"] / df["category_mean_value"]

The danger here is volume: you can generate hundreds of ratios, and some will look predictive by chance. Create features because you can explain why they should matter.

E. Text features

Text must become numbers first. Simple signals go a long way: review length, word count, number of exclamation marks. Word frequency (bag of words) counts how often each word appears. TF-IDF weights those counts so that a word that is frequent in one review but rare overall ("broken") counts more than one that appears everywhere ("the"). Both are forms of text vectorization: each text becomes a row of numbers.

from sklearn.feature_extraction.text import TfidfVectorizer

df["review_length"] = df["review"].str.len()
tfidf = TfidfVectorizer(max_features=50, stop_words="english")
X_text = tfidf.fit_transform(df["review"])      # sparse matrix: one column per word

TF-IDF ignores word order and meaning ("not good" looks like "good"), and the vocabulary comes from the training data, so fit it on training data only.

F. Missing values and outliers

Missing-value imputation fills gaps, for example with the median for numbers or the most frequent value for categories. Missingness indicators are extra 0/1 columns saying "this value was missing". Imputing alone hides the gap. The indicator keeps it, which matters when missing is itself informative (a customer who never gave an age may behave differently).

The two are different jobs. Imputation handles missing data so the model can run. An indicator creates a feature from the fact that data was missing. Often you do both.

from sklearn.impute import SimpleImputer

imp = SimpleImputer(strategy="median", add_indicator=True)   # fills gaps + adds flag columns

Outliers need a decision, not a rule. Capping values at the IQR fences (Q1 − 1.5 × IQR and Q3 + 1.5 × IQR; see IQR) limits their influence. But a €900 order may be a real, valuable customer. Check what an outlier is before you change it, and prefer capping or a log transform over deleting rows.

q1, q3 = df["order_value"].quantile([0.25, 0.75])
iqr = q3 - q1
df["value_capped"] = df["order_value"].clip(q1 - 1.5 * iqr, q3 + 1.5 * iqr)

Practical Implementation with Python

The running example is an e-commerce shop. We want customer-level features to predict churn, defined as no order in the 90 days after a cut-off date (30 June 2026). Every feature may only use orders up to that date. The data is simulated, so the numbers show the method, not real customer behavior.

The simulated shop data

This block creates one table with one row per order (orders) and one with one row per customer (customers, including the target churned). You can skip the details and focus on the result.

import numpy as np
import pandas as pd

rng = np.random.default_rng(42)
n_customers = 4000
obs_start = pd.Timestamp("2025-07-01")
cutoff = pd.Timestamp("2026-06-30")
label_end = pd.Timestamp("2026-09-28")                # cut-off + 90 days

customers = pd.DataFrame({
    "customer_id": np.arange(1, n_customers + 1),
    "age": rng.integers(18, 75, n_customers).astype(float),
    "country": rng.choice(["DE", "AT", "CH", "NL"], n_customers, p=[.6, .1, .1, .2]),
})
customers.loc[rng.random(n_customers) < 0.08, "age"] = np.nan    # 8% missing ages

orders = []
for cid in customers["customer_id"]:
    rate = rng.gamma(2.0, 0.6)                        # orders per month
    basket = rng.lognormal(mean=3.8, sigma=0.5)       # typical basket value in EUR
    active_until = obs_start + pd.Timedelta(days=float(rng.exponential(330)))
    t = obs_start + pd.Timedelta(days=float(rng.exponential(30 / rate)))
    while t < label_end and t < active_until:
        orders.append((cid, t.normalize(), round(rng.lognormal(np.log(basket), 0.4), 2)))
        t += pd.Timedelta(days=float(rng.exponential(30 / rate)) + 1)
orders = pd.DataFrame(orders, columns=["customer_id", "order_date", "order_value"])
orders["order_id"] = np.arange(1, len(orders) + 1)

# target: 1 = no order in the 90 days after the cut-off
ordered_later = set(orders.loc[orders["order_date"] > cutoff, "customer_id"])
has_history = set(orders.loc[orders["order_date"] <= cutoff, "customer_id"])
customers = customers[customers["customer_id"].isin(has_history)].copy()
customers["churned"] = (~customers["customer_id"].isin(ordered_later)).astype(int)

Building customer-level features

The goal is one row per customer. We group the orders by customer and calculate what each history says about future behavior.

snapshot_date = cutoff + pd.Timedelta(days=1)       # 1 July 2026
past = orders[orders["order_date"] < snapshot_date].sort_values(["customer_id", "order_date"])

features = past.groupby("customer_id").agg(
    total_orders=("order_id", "count"),
    total_spent=("order_value", "sum"),
    first_order=("order_date", "min"),
    last_order=("order_date", "max"),
)

features["avg_order_value"] = features["total_spent"] / features["total_orders"]
features["recency_days"] = (snapshot_date - features["last_order"]).dt.days
features["tenure_days"] = (snapshot_date - features["first_order"]).dt.days
features["orders_per_month"] = features["total_orders"] / (features["tenure_days"].clip(lower=30) / 30)

# average time between purchases (NaN for customers with a single order)
gaps = past.groupby("customer_id")["order_date"].diff().dt.days
features["avg_days_between_orders"] = gaps.groupby(past["customer_id"]).mean()
features["recency_vs_usual_gap"] = features["recency_days"] / features["avg_days_between_orders"]
features["single_order_flag"] = features["avg_days_between_orders"].isna().astype(int)

recent = past[past["order_date"] > snapshot_date - pd.Timedelta(days=90)]
features["orders_last_90d"] = recent.groupby("customer_id")["order_id"].count()
features["orders_last_90d"] = features["orders_last_90d"].fillna(0)

features = features.drop(columns=["first_order", "last_order"])
df = customers.set_index("customer_id").join(features, how="left")

What each feature says about the customer:

  • total_orders, total_spent. How much history the customer has and how valuable they are.
  • avg_order_value. Spending per order, separate from how often they buy.
  • recency_days. How long the customer has been silent. In churn problems this is usually the strongest signal.
  • orders_per_month. Purchase frequency, adjusted for how long the customer has existed (clip(lower=30) stops brand-new customers from getting absurd rates).
  • avg_days_between_orders, recency_vs_usual_gap. The customer's own rhythm. A value above 1 means they are already overdue compared with their normal pattern.
  • single_order_flag. The gap is undefined for one-order customers, so we keep the fact that it's missing as its own feature.
  • orders_last_90d. Recent activity compared with the whole history.

Feature Selection and Feature Importance

Feature engineering makes candidate features. Feature selection decides which to keep. More features do not automatically mean a better model: each one adds noise the model can latch onto, the risk of overfitting grows (see Overfitting and Underfitting), and the model gets harder to explain. Variable Selection vs. Regularization covers the logic in depth.

Start with the obvious: drop IDs, constant columns and exact duplicates. Then look at how the remaining features relate to each other.

Correlation and multicollinearity

If two features say nearly the same thing (log_order_value and order_value), keep one. For linear models, strongly correlated features make coefficients unstable and hard to interpret.

Filter, wrapper and embedded methods

  • Filter methods score each feature on its own, before any model (for example, an ANOVA F-test with SelectKBest). They are fast but ignore interactions.
  • Wrapper methods train models repeatedly on different subsets. Recursive Feature Elimination (RFE) removes the weakest feature step by step. They are more accurate but slower.
  • Embedded methods select during training. L1 regularization (Lasso) shrinks some coefficients to exactly zero, and tree models rank features by how much they improve splits.
from sklearn.ensemble import RandomForestClassifier
from sklearn.feature_selection import RFE, SelectFromModel, SelectKBest, f_classif
from sklearn.linear_model import LogisticRegression

SelectKBest(f_classif, k=5)                                                  # filter
RFE(LogisticRegression(max_iter=1000), n_features_to_select=5)               # wrapper
SelectFromModel(RandomForestClassifier(n_estimators=200, random_state=42))   # embedded

All three learn from the data, so in practice they belong inside the training part of a pipeline (see the pipeline section below).

Tree-based importance

Tree models are convenient because they report how much each feature contributed. But the built-in impurity importance tends to favor continuous features and splits credit between correlated ones. permutation_importance is a more honest check: it shuffles one feature on held-out data and measures how much the score drops.

PCA and dimensionality reduction

PCA is dimensionality reduction rather than selection. It combines features into a few new, uncorrelated components that keep most of the variance. It helps with many correlated numerical features, but the components are hard to explain ("component 2" is not a business concept), so it's rarely the first choice when interpretability matters.

Feature Engineering in a Machine Learning Pipeline

Feature engineering belongs inside the workflow, in this order: split the data, fit transformations on the training part, train, then evaluate on the test part.

Fit on training data only

Every transformation that learns something from the data must be fitted on the training data only. Scalers learn means, imputers learn medians, encoders learn categories, target encoders learn target averages. If they see the test set, information leaks from the test set into the model, and your test score becomes too optimistic.

Data leakage

Using information at training time that wouldn't be available when predicting on genuinely new data. The result is a test score that looks better than the real-world performance will be.

# WRONG: the scaler learns mean and std from ALL rows, including the test set
X_scaled = StandardScaler().fit_transform(df[num_cols])
X_train, X_test = train_test_split(X_scaled, test_size=0.25)
from sklearn.model_selection import train_test_split
from sklearn.preprocessing import StandardScaler

num_cols = ["age", "total_orders", "total_spent", "avg_order_value", "recency_days",
            "tenure_days", "orders_per_month", "avg_days_between_orders",
            "recency_vs_usual_gap", "single_order_flag", "orders_last_90d"]
cat_cols = ["country"]
y = df["churned"]

# RIGHT: split first, then learn only from the training part
X_train, X_test, y_train, y_test = train_test_split(
    df, y, test_size=0.25, stratify=y, random_state=42)
scaler = StandardScaler().fit(X_train[["total_spent"]])
X_test_scaled = scaler.transform(X_test[["total_spent"]])    # transform only, never fit

Pipeline and ColumnTransformer

Doing this by hand for every step is error-prone. A Pipeline chains steps, and a ColumnTransformer applies different steps to numerical and categorical columns. When you call fit, everything is learned from the training data only, and the same steps are applied to new data automatically.

from sklearn.compose import ColumnTransformer
from sklearn.impute import SimpleImputer
from sklearn.linear_model import LogisticRegression
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import OneHotEncoder

def make_preprocess(num_cols, cat_cols):
    numeric = Pipeline([
        ("impute", SimpleImputer(strategy="median", add_indicator=True)),  # fill + missing flag
        ("scale", StandardScaler()),
    ])
    categorical = OneHotEncoder(handle_unknown="ignore")   # unseen categories become all zeros
    return ColumnTransformer([("num", numeric, num_cols), ("cat", categorical, cat_cols)])

model = Pipeline([
    ("prep", make_preprocess(num_cols, cat_cols)),
    ("clf", LogisticRegression(max_iter=1000, class_weight="balanced")),
])
model.fit(X_train[num_cols + cat_cols], y_train)

handle_unknown="ignore" prevents a crash when the test data contains a country the training data never saw. class_weight="balanced" stops the model from ignoring the smaller class.

A second kind of leakage: time

No pipeline fixes time leakage. If a feature uses orders after the cut-off date, the model sees the future. Here that is prevented because every feature was built from past only. Always ask: "Would I have known this at prediction time?"

Does Feature Engineering Improve Model Performance?

Not automatically, so we test it.

The experiment

Same customers, same train/test split (75/25, stratified), same two models (logistic regression and random forest), but two feature sets.

  • Baseline. age, country, total_orders, total_spent: what a plain group-by gives you.
  • Engineered. The baseline plus avg_order_value, recency_days, tenure_days, orders_per_month, avg_days_between_orders, recency_vs_usual_gap, single_order_flag and orders_last_90d.

The metrics treat churn as the positive class. Accuracy is the share of all customers classified correctly. Precision is, of the customers flagged as churners, the share who really churned. Recall is, of the real churners, the share the model found. F1 combines precision and recall. The confusion matrix shows the four counts behind them. Common Logistic Regression Metrics explains each of them step by step.

from sklearn.ensemble import RandomForestClassifier
from sklearn.metrics import classification_report, confusion_matrix

baseline_num = ["age", "total_orders", "total_spent"]
engineered_num = num_cols

estimators = {
    "logreg": lambda: LogisticRegression(max_iter=1000, class_weight="balanced"),
    "rf": lambda: RandomForestClassifier(n_estimators=300, min_samples_leaf=5,
                                         class_weight="balanced", random_state=42, n_jobs=-1),
}
for feature_set, cols in {"baseline": baseline_num, "engineered": engineered_num}.items():
    for name, make_estimator in estimators.items():
        pipe = Pipeline([("prep", make_preprocess(cols, cat_cols)), ("clf", make_estimator())])
        pipe.fit(X_train[cols + cat_cols], y_train)
        pred = pipe.predict(X_test[cols + cat_cols])
        print(feature_set, name)
        print(classification_report(y_test, pred, digits=3))
        print(confusion_matrix(y_test, pred))

How to interpret the results

  • The baseline barely beats a trivial rule. Its accuracy of 0.709 is hardly above the 0.70 you get by always predicting churn, so the raw aggregates add little.
  • The engineered set cuts both kinds of error. False alarms (retained customers wrongly flagged) drop from 95 to 24, and missed churners drop from 162 to 91. For a retention campaign with costly offers, fewer false alarms is the main business gain.
  • The pattern holds across models. Logistic regression and random forest both improve, which suggests the gain comes from the features and not from one model's quirks.

What this does and does not prove

The simulation makes churn depend on how long a customer has been silent, so recency features are expected to help here. The experiment shows how to test the idea, not that feature engineering always works.

On real data, use cross-validation instead of a single split, compare against a simple baseline, and ask whether a gain is large enough to matter for the business. A feature that adds 0.2 percentage points but takes a week to maintain may not be worth it.

Key takeaway

Feature engineering combines technical skill with domain knowledge: the best features usually come from understanding how the business works. A better representation can help a model learn the same pattern with less effort, but more features do not automatically mean a better model, and every transformation must be fitted on training data only. Before choosing an algorithm, spend time with the data itself, because most modeling problems that look like algorithm problems turn out to be data representation problems.
